# Real TLS 1.3 handshake phase profile

This baseline measures a real TLS 1.3 handshake against a local OpenSSL server
and records the library's exclusive phase timings. It answers the question left
open by the self-test rows: where does handshake time actually go on Palm OS?

Measured after `702a330` (HTTP header parser fix) with the ARM image
`e5bd1779eeaed6bddbf3504148cb5c0219581784746db5670f19b3538cfb29b1`
(49,636 bytes), `cp-uarm` at 100 MIPS, 10 ms Palm tick resolution, and five
samples per case in two independent runs.

The fixture is generated by [`handshake-server.py`](../../handshake-server.py):
TLS 1.3, ECDSA P-256 certificates signed with SHA-256, and an 8-certificate PEM
trust bundle (4,560 bytes). The server independently confirmed 20 full and 10
resumed TLS 1.3 connections per run; each sample negotiates the same cipher.

## Method

```sh
python3 library/bench/run-handshake.py \
    --emulator /path/to/cp-uarm \
    --session /path/to/session_os5.img \
    --output library/bench/baselines/2026-11-17-arm-handshake-profile \
    --mips 100
```

The harness starts the fixture server, builds `PalmTLSHandshakeBench.prc`,
installs it with the library PRC, runs the six cases, exports the results
database, and validates that every phase sum equals the measured handshake
duration. The fixture directory contains development-only keys and is not
committed; `run/` and `repeat1/` keep the results, metadata, server log and
summary.

## Handshake medians

| Case | Handshake | Load | Post |
| --- | ---: | ---: | ---: |
| `cache_full_cold` | 330 ms | 80 ms | 10 ms |
| `cache_full_warm` | 210 ms | 0 ms | 10 ms |
| `cache_resumed` | 110 ms | 0 ms | 10 ms |
| `nocache_full_cold` | 330 ms | 80 ms | 10 ms |
| `nocache_full_warm` | 330 ms | 0 ms | 10 ms |
| `nocache_resumed` | 230 ms | 0 ms | 10 ms |

`repeat1` reproduces every median exactly; its per-sample maxima differ by at
most one tick.

## Exclusive handshake phases

Values are medians in milliseconds; empty cells are zero.

| Phase | cache full cold | cache full warm | cache resumed | nocache full cold | nocache resumed |
| --- | ---: | ---: | ---: | ---: | ---: |
| other | 10 | | 10 | 10 | 10 |
| trust | 120 | | | 120 | 120 |
| key share | 30 | 30 | 30 | 30 | 30 |
| key agreement | 40 | 50 | 40 | 40 | 40 |
| certificate | 20 | 20 | | 20 | |
| signature | 80 | 90 | | 90 | |
| KDF | 20 | 20 | 30 | 30 | 20 |

A resumed handshake verifies no certificate, so it has no certificate or
signature phase. It still pays the trust phase unless the context is cached,
because the engine loads the CA store before every non-reusable handshake.

### ECDHE detail (key agreement)

| Sub-phase | Time |
| --- | ---: |
| import | 10 ms |
| validate | 0 ms |
| multiply | 30 ms |
| map | 0 ms |

The variable-base P-256 multiply dominates key agreement. Client key-share
generation is a separate 30 ms phase, so the two P-256 operations together cost
about 60–70 ms per full handshake.

### Load detail (cold open)

| Sub-phase | Time |
| --- | ---: |
| copy | 10 ms |
| relocate | 40–50 ms |
| native | 20 ms |
| qualify | 10 ms |

### Trust detail (uncached)

| Sub-phase | Time |
| --- | ---: |
| PEM-to-DER | 70 ms |
| certificate decode | 40–50 ms |
| store | 0–10 ms |

PEM conversion dominates. A caller that supplies DER (as the TLS Tester does
with its pinned anchors) avoids most of that cost, but a PEM bundle is
re-parsed for every new host context.

## Findings

1. **Signature verification is the largest warm-handshake phase** at 80–90 ms.
   The direct `wc_ecc_verify_hash` benchmark row is about 40 ms, and the
   instrumented sub-phases only account for DER decode (10 ms), order
   arithmetic (0–10 ms) and the native double-scalar (20–30 ms). The remaining
   time sits in the `DoTls13CertificateVerify` wrapper and certificate-key
   import, which need finer instrumentation before changing native code.
2. **P-256 ECDHE costs about 70 ms** (30 ms key share + 40–50 ms key
   agreement, of which 30 ms is the variable-base multiply). This is the
   second-largest block and the main argument for X25519 support.
3. **Cold trust setup costs 120 ms** and is paid per new host when the context
   cache misses. Reusing a parsed CA store across host contexts, or converting
   PEM anchors to DER at install time, removes most of it.
4. **Context and session reuse work.** A reused context saves 120 ms
   (`cache_full_warm` 210 vs `nocache_full_warm` 330), and a resumed session
   saves another 100 ms (110 vs 210). A client that keeps contexts and sessions
   alive avoids nearly all handshake cost on repeat requests.
5. **KDF is 20–30 ms**, larger than expected for a few HMAC-SHA256 calls; it
   deserves a closer look once the larger phases are addressed.

## Caveats

- Palm ticks are 10 ms, so phases at 10–30 ms are quantized. Only the 80–120 ms
  phases support confident comparisons.
- `cp-uarm` is instruction-budgeted and does not model caches, memory wait
  states or physical PXA270 timing. These numbers are not device measurements.
- The fixture's PEM bundle is deliberately realistic for a bundled trust store.
  A single DER anchor, as used by the TLS Tester, has a much smaller trust
  phase.
- The handshake benchmark does not exercise RSA chains or downloads; use the
  TLS Tester and the record benchmark for those paths.
